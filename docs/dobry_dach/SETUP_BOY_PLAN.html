Kluczowa zmiana architektury vs poprzedni plan

Firma ma komputer który chodzi 24/7 — tam mieszka Claude Desktop i tam stanie Python runner. Brak VPS, brak Tailscale. Runner widzi SQL Server przez LAN (sieć lokalna biura), nie przez tunel. Zarządzanie przez RDP = wirtualny dostęp Tomka. Prościej, taniej, mniej punktów awarii.

⚠ Wciąż krytyczne — dwie bazy

Klient ma dwie bazy: komandytową (mamy kopię) + jawną (faktury do klienta, sprzedaż usług). Bez jawnej A6 pokazuje pół obrazu. Dostęp SELECT na jawnej = priorytet #1. Jeśli obie bazy są na tej samej instancji SQL → jedno konto dd_auto, dwa GRANT SELECT.

🔧 Architektura — maszyna always-on jako centrum

Runner i model na tej samej maszynie w biurze. Baza lokalna przez LAN. Claude Desktop widzi logi — nie widzi surowych danych z bazy.

Dlaczego maszyna always-on > VPS

Runner musi widzieć bazę SQL. Baza stoi w LAN biura. Maszyna already-on jest w tym samym LAN → połączenie bezpośrednie, bez tunelu, zero opóźnień sieciowych, zero abonamentu. Kto to podnosi o 7 rano gdy nie wyszedł raport? Tomek przez RDP — dokładnie tak samo jak przez SSH do VPS-a, tylko bez dodatkowej maszyny.

RUNNER (Python)

Co robi na maszynie

Łączy się z SQL Server przez LAN, liczy deterministycznie (marże, portfele, ZK vs WZ), wysyła maile, zapisuje do kalendarzy. Dane nie wychodzą z sieci biura — nie ma dokąd.

MODEL (Claude API)

Co robi w chmurze

Dostaje tylko to, co runner mu wyśle: treść skanu projektu dla A1. Nie widzi bazy, nie liczy pieniędzy. Claude Desktop widzi logi z raportu — nie surowe dane kontrahentów.

    Godzina 1 — Rozpoznanie przez RDP

    Zanim cokolwiek instalujesz — patrz. Maszyna always-on może mieć już Python, może mieć inne procesy których nie chcesz tknąć.
    • Połącz przez RDP do maszyny always-on
    • python --version lub python3 --version — czy jest? jaka wersja?
    • Sprawdź Task Scheduler — czy są już zaplanowane zadania, kto je ustawił
    • Ping do instancji SQL Server: ping <nazwa-instancji> i Test-NetConnection -ComputerName <host> -Port 1433
    • Potwierdź: baza jawna na tej samej instancji co komandytowa (jedno okno Management Studio → sys.databases)
    • Kto ma dostęp admina SQL? Czy jest na miejscu teraz?

  • G2

    Godzina 2 — Python + konto SQL

    Instalacja środowiska i konto read-only. Wszystko przez RDP.
    • Python 3.11 jeśli nie ma (python.org, instalator .exe, dodaj do PATH)

    • Admin SQL zakłada konto dd_auto: CREATE LOGIN + CREATE USER + db_datareader na obu bazach

  • G3

    Godzina 3 — A6 na produkcji

    Jeden działający automat > osiem w planach. Dry-run → akceptacja klienta → ostro → Task Scheduler.
    • Uzupełnij .env: hasła DB (komandytowa + jawna), SMTP, refresh token GCal
    • Dry-run: python auto4_final.py --dry-run → raport na ekranie bez wysyłki
    • Pokaż klientowi: "czy to co widzisz zgadza się z tym co masz w Subiekcie?"
    • Ostro: python auto4_final.py → mail idzie na dwie skrzynki
    • Task Scheduler: nowe zadanie → C:\dd-automaty\venv\Scripts\python.exe C:\dd-automaty\auto4_final.py, trigger: codziennie 7:00, uruchamiaj nawet gdy użytkownik wylogowany (konto serwisowe lub SYSTEM)
    • Watchdog 7:05 — to samo Task Scheduler, osobne zadanie
    • Kryterium: mail odebrany na obu skrzynkach, 3 PH ręcznie sprawdzone
    ~45 min

💬 Jak to powiedzieć klientowi

Co to jest i po co

"Python robi wszystkie liczenia na waszym komputerze — baza, kalendarze, maile. Claude to głowa, która dostaje tylko wyniki. Dane klienta nie wychodzą z waszej sieci."

Dlaczego maszyna w biurze, nie zewnętrzny serwer

"Baza SQL jest w waszej sieci. Runner musi ją widzieć. Komputer który chodzi 24/7 jest w tej samej sieci — połączenie bezpośrednie, zero abonamentów, zero dodatkowych maszyn."

Co dostajecie dziś vs co jest w kolejce

"Dziś ruszamy jeden automat: codzienny raport portfeli handlowców. Sprawdzony, gotowy. Reszta wchodzi tydzień po tygodniu — jak zdejmiemy kolejne blokady."

Runda 2 — skąd się bierze

"Jak automaty będą działać stabilnie 4 tygodnie, zaczniemy budować agenta kontraktu — takiego PM-a dla dużych zleceń jak NDI. Ten sam komputer, ta sama baza — tylko dodajemy warstwy."

⚠ Truth Checker

Co wiem: Maszyna always-on istnieje (RDP do pośredniczącego komputera). Claude Desktop zainstalowany. A6 end-to-end przetestowane. OAuth Calendar działa. SMTP potwierdzone. Wirtualny dostęp aktywny.

Co zakładam: Maszyna always-on ma dostęp do sieci LAN z SQL Serverem. Python może być zainstalowany lub nie. Konto SYSTEM może uruchamiać Task Scheduler bez logowania.

Co może być błędne: SQL Server może wymagać uwierzytelnienia Windows (nie SQL Login) → konto dd_auto musi być kontem domenowym, nie SQL Login. Task Scheduler w trybie SYSTEM może nie mieć dostępu do zasobów sieciowych. Port 1433 może być zablokowany firewallem między maszyną a SQL Serverem.

Co zweryfikuj na starcie RDP: Test-NetConnection port 1433. Tryb uwierzytelnienia SQL Server (SQL + Windows vs tylko Windows). Wersja Python i dostępność pip.

Co poprawię z jednym inputem: Jeśli poznasz OS maszyny always-on (Windows/Linux) i tryb auth SQL Servera (Mixed Mode vs Windows Only) — checklista Z0 stanie się jeszcze bardziej konkretna.
