1.Cel główny

Budowa automatyzacji w oparciu o kluczowy proces biznesowy i kluczowe dane klienta:

  • baza danych z Subiekta (komandytowa + jawna)
  • kilka raportów Excel (np. raport kasowy)

  • maile jako narzędzie komunikacji — ale i (chyba) źródło wiedzy o powodach zmian
Fundament (najważniejsze założenie)

Runner (Python) czyta bazę Subiekta read-only · wiedza o firmie żyje w folderze .md · oba na maszynie w biurze, nigdy nie zasypiającej (decyzja 26.08: zero VPS, zero Tailscale). Bez dostępu do bazy nie ma nic.

2.Założenia — 8 punktów

  1. Setup lokalny — jeden konkretny lokalny folder z wiedzą (skille i reszta w jednym miejscu).
  2. Second brain = folder .md (Obsidian), nie baza danych. Obsidian = tylko edytor — zero lock-inu. Postgres dopiero gdy automaty zaczną pisać dane strukturalne.
  3. Chatbot w sieci biura (LAN) — ludzie pytają przez przeglądarkę na maszynę always-on (RAG, cytuje źródło). Folder = wiedza stała · baza = stan na dziś — pytania „żywe" (asortyment) wymagają mostu runnera.
  4. Osobny vault DD, osobny vault TW — jedna metoda. Wiele zbiorów w jednym vaultcie: Procesy / Asortyment / Klienci / Automaty / Ludzie / Czat-publiczny.
  5. Sposób budowy agentów (wzorzec CASE_STUDY_AGENT_Z_WIKI): czytanie wiedzy = krok procesu, nauka wraca do pliku, który czyta kod. KANON · MASZYNA · TRIKI+ZAKAZY · RESEARCH · CBA. Cel: agenci/bazy CRO wg tego wzorca.
  6. STRAŻNIK — audytor procesu (głowa, w centrum). Czyta bazę (4 lata historii) i mierzy proces: cykle ZK→WZ→FV, dziury, „jak ma być vs jak jest". Raport dziur co tydzień → dziura = kandydat na automat/regułę. Automaty = egzekucja, strażnik = detekcja. Persona: NIE — rola z protokołem i ZAKAZAMI.
  7. Watchdog — robotnik strażnika, i to NAPRAWIACZ. Zbiera logi; wykrył → naprawia sam (restart, ponów wysyłkę, rollback); alert po 2 nieudanych próbach. Ciche samonaprawienie = zero hałasu.
  8. Boty — warstwa komunikacyjna z ludźmi. Kanał: WhatsApp, nie Discord. Boty: biurowy (LAN), terenowy (WhatsApp + głos), publiczny (strona). Marzenie: ludzie dzwonią do botów, boty rejestrują (wymaga mappingu procesu).
  9. Repo HTML/dokumentów — osobne od folderu wiedzy. Istnieje: ai4cro-reports (GH Pages) → docs/dobry_dach/.

10.Jak pracuje Claude / Hermes (podział ról)

Zasada współpracy

Runner robi to, co wymaga determinizmu (liczby, wysyłka). Claude/Hermes robi to, co wymaga rozumienia (treść, plan, decyzja). Claude nie widzi bazy SQL — widzi tylko raporty i logi, które runner wygenerował. Kontrakt między nimi: pliki (JSON/HTML/log) w znanych ścieżkach. Zawsze można sprawdzić, co runner zrobił — logi są, raport jest.

Dlaczego HTML na localhost, nie apka?

Zero zależności: python http.server + statyczne pliki. Działa na maszynie w biurze bez instalacji czegokolwiek. Jak zaufamy — można wystawić w LAN dla klienta (czytanie). Docelowo interfejs = zakładka w dd-jeden (jeśli maszyna będzie miała publiczny adres) albo osobna podstrona.

Run D3 = Twój przykład, rozpisany

„Ustal czy WZ ma pokrycie we wpływie": bierzemy WZ (typ 11) z okna (dziś/wczoraj/14 dni), kwalifikujemy każdy wg algorytmu — ① ZK wskazuje WZ → pokryte, ② pole na WZ = FS/FZ lub wspólna pozycja → pokryte, ③ PA → pokryte (detal), ④ KFZ dziedziczy → pokryte, ⑤ nic → GOŁE (dziura — towar wyjechał bez dokumentu). GOŁE starsze niż 1 dzień = realna dziura do pokazania. To jest N4 w jednym zapytaniu — run używa tej samej logiki co raport dzienny.

13.Wiedza jako asset — serce systemu

Problem, który Tomek nazwał wprost

Cała wiedza zebrana w tym projekcie (proces-roboczy 18 węzłów, STRUKTURA_WEZLOW.json, KB, AUTOMATYZACJE, odkrycia) nie jest używana przez system — żyje w HTML dla ludzi, a automaty działają na zapytaniach SQL pisanych obok. To błąd: strona z procesem (co wiemy i jak działa) jest święta — powinna być fundamentem, z którego system czyta, a nie dokumentacją obok.

Docelowy układ — wiedza jest jedynym źródłem konfiguracji, nie ozdobą:

Kierunek: wiedza → system, nie system → wiedza

Automat nie ma swojej prywatnej prawdy w kodzie. Definicje (co to GOŁE, jaki próg marży, kto jest PH) mieszkają w wiedzy; kod je czyta. Zmiana definicji = zmiana w wiedzy, nie w 5 skryptach. Agent Procesu pilnuje, żeby wiedza i kod się nie rozjechały (run D6 + SYNC po każdej zmianie).
