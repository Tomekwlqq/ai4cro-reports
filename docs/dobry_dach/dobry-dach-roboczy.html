Dobry Dach
— pełny obraz procesów

Dokument roboczy na bazie drugiego pliku — znacznie więcej szczegółów. Cały cykl od ZK do FV finalnej, rola PH, system alertów, dzienne summary. Iterujemy w czacie.

📖 Pojęcia kluczowe

Słownik

Pojęcia pojawiające się w procesach — żebyśmy mówili tym samym językiem.

ZK
Zlecenie Klienta — centralna jednostka systemu. Ma statusy, wiele ZK może być powiązanych z jednym projektem. ZK = kontrakt w oczach systemu.
WZ
Wydanie Zewnętrzne — dokument wydania towaru / materiałów. Tworzony w trakcie realizacji, powiązany z ZK. Kilka WZ na jedno ZK.
FV
Faktura VAT — wystawiana za etapy (zaliczki w trakcie) oraz finalna (rozliczenie różnic). Model: ~90% w trakcie + ~10% końcowa.
PH
Przedstawiciel Handlowy — opiekun klienta. Powinien znać status realizacji ZK, ale w praktyce często nie wie. Kluczowy odbiorca automatyzacji #4.
GW
Generalny Wykonawca — zleceniodawca przy dużych kontraktach. Narzuca format oferty i jednostki przeliczeniowe.
Marża Tomasza
Plik Excel do liczenia marży per item — kluczowe narzędzie przy ofertowaniu. Cel: zastąpić / zautomatyzować.

1 Priorytet #1 · Małe automatyzacje

Generowanie oferty (ZK)
+ AI scan projektu

Klient przychodzi z projektem (scan/PDF). Agent wizyjny wyciąga kluczowe parametry, mapuje na cennik, liczy marżę z pliku Tomasza i generuje ZK gotowe do wysyłki. Często też: powielenie poprzedniego ZK jako baza.

⚡Jak to działa — krok po kroku
Propozycja▶
  • 1
    Upload skanu projektu — klient przynosi PDF lub zdjęcie projektu. Użytkownik wgrywa do aplikacji.
  • 2
    Agent wizyjny (Claude Vision) — wyciąga: powierzchnia dachu, typ krycia, obróbki, świetliki. Pokazuje wynik do weryfikacji przed liczeniem.
  • 3
    Opcja: powiel poprzednie ZK — agent proponuje "masz podobny projekt z [data], użyć jako bazę?" i nadpisuje tylko to co się różni.
  • 4
    Mapowanie na cennik — parametry z projektu → pozycje z systemu magazynowego → ceny.
  • 5
    Kalkulacja marży (logika Tomasza) — agent replikuje algorytm z pliku Excel: marża per item, narzuty, podsumowanie. Użytkownik widzi roboczą kalkulację.
  • 6
    Rezerwacja stanów magazynowych — opcjonalnie: po akceptacji ZK agent blokuje stany (jeśli API pozwala).
  • 7
    Generowanie ZK — dokument oferty w docelowym formacie (Excel / Word / PDF), gotowy do wysyłki do klienta.

2 Małe automatyzacje

Umowa, formalności
i Google Calendar

Po akceptacji wyceny: przygotowanie umowy, weryfikacja formalna przez AI, wbicie dat do Google Calendar, zmiana statusu ZK → "do realizacji", automatyczne zamówienie materiałów.

⚡Jak to działa
Propozycja▶
  • 1
    Przygotowanie umowy — agent generuje projekt umowy na bazie zatwierdzonego ZK i szablonu. Parametry z ZK wchodzą do umowy automatycznie.
  • 2
    Negocjacje — zmiany nanoszone w aplikacji, agent śledzi delta (co się zmieniło vs pierwotne ZK).
  • 3
    Weryfikator AI (formalności) — przed podpisaniem: agent sprawdza umowę pod kątem braków formalnych (brak dat, nieprawidłowe dane, brakujące klauzule). Flaguje problemy.
  • 4
    Akceptacja → zmiana statusu ZK — po podpisaniu agent zmienia status ZK na "do realizacji" i triggeruje kolejne kroki.
  • 5
    Wpis do Google Calendar — data transportu, data realizacji — wbijane automatycznie do kalendarza odpowiedniego PH/ekipy.
  • 6
    Zamówienie materiałów — na podstawie ZK generuje zamówienie do dostawcy.
🔧Architektura techniczna
Tech▶
Umowapython-docx na szablonie DOCX — parametry z ZK wchodzą przez zmienne
Weryfikator AIClaude API — prompt: "sprawdź umowę pod kątem braków: daty, strony, przedmiot, wartość, kary, gwarancja". Output: lista problemów z priorytetem.
Google CalendarGoogle Calendar API (OAuth 2.0) — tworzenie eventu per ZK z datą transportu i realizacji, przypisanie do kalendarza PH
Zmiana statusu ZKZależy od systemu magazynowego — API call lub wpis do bazy. Do weryfikacji.
❓Pytania otwarte
Do wyjaśnienia▶
Szablon umowyCzy jest aktualny szablon Word? Ile wariantów (różne typy klientów, różne zakresy)?
Google Calendar — strukturaIle kalendarzy? Per PH, per ekipa, per projekt? Kto teraz wpisuje daty?
Zmiana statusu ZKCzy system pozwala to robić przez API, czy to ręczna operacja w interfejsie systemu?
3 Małe automatyzacje

Realizacja: WZ, zmiany
i raportowanie

W trakcie realizacji powstają zamówienia częściowe i WZ. PH powinien wiedzieć o każdej zmianie — i teraz nie wie. Agent monitoruje i powiadamia.

⚡Jak to działa
Propozycja▶
  • 1
    Monitoring WZ — agent śledzi nowe WZ powiązane z ZK. Kiedy pojawia się zmiana, triggeruje powiadomienie.
  • 2
    Powiadomienie PH — "Dla ZK #1234 (Kowalski, 400m²) wyszło WZ #56: materiały X, wartość Y. Postęp realizacji: 34%." Via mail lub SMS.
  • 3
    Obsługa zmian zakresu — klient zmienia zakres w trakcie: agent rejestruje zmianę, przelicza wartość ZK, flaguje różnicę do zatwierdzenia.
  • 4
    Zamówienia częściowe — na bazie WZ agent generuje zamówienie częściowe do dostawcy. Ręczna praca teraz, automatyczna po wdrożeniu.
  • 5
    Płatności za etapy — gdy etap zamknięty (WZ wystawione, PH potwierdził), agent tworzy FV zaliczkową i wysyła do klienta.
🔧Architektura techniczna
Tech▶
Monitoring WZPolling systemu magazynowego co N minut (lub webhook jeśli system to obsługuje) — nowe WZ per ZK
Powiadomienia PHE-mail (SMTP) lub SMS (np. Twilio). Format: krótki, konkrety, link do ZK.
Obliczenie postępuSuma wartości WZ ÷ wartość umowna ZK = % realizacji. Python, zero AI.
FV zaliczkowaZależy od systemu fakturowania — czy jest to samo narzędzie co ZK/WZ? Do weryfikacji.
❓Pytania otwarte
Do wyjaśnienia▶
Jak WZ jest teraz tworzony?Kto wystawia WZ — magazynier, PH, system automatycznie? Czy jest ręczny etap "wydaj materiały"?
Skąd PH ma dostawać powiadomienia?Mail, SMS, push w appce, wiadomość WhatsApp? Co faktycznie przeczyta?
Faktury — jaki system?Czy FV są w tym samym systemie co ZK/WZ, czy osobny program (np. iFirma, Fakturownia, Comarch)?
4 Małe automatyzacje · Wysoki priorytet

Dzienne summary
dla PH

Codziennie rano PH dostaje jedno zestawienie: wszystkie jego ZK, ich statusy, wartości, co wyjechało, co zapłacono. Zero pytań do magazynu — wszystko w jednym miejscu. "Weź pigułkę" — cytat z prezentacji.

▶
Dobry dzień, Tomasz — Twój raport na sobotę, 2 sierpień 2026 W tym tygodniu masz 17 zamówień dla 12 klientów. Do realizacji poszło dziś: 5. Wyjechały: 5. Zaległe płatności: 3 z 8 zamówień. ──────────────────────────────────── AKTYWNE ZAMÓWIENIA (12) ZK #1201 · Kowalski, 450m² papa SBS Wartość umowna: 48 000 PLN Wydane WZ (koszt): 21 400 PLN ▌▌▌▌▌░░░░░ 44% Wartość sprzedaży: 31 200 PLN Wpłaty: 28 000 PLN BRAKUJE: 3 200 PLN ZK #1198 · Firma ABC Sp. z o.o. Wartość umowna: 72 000 PLN Wydane WZ (koszt): 8 600 PLN ▌▌░░░░░░░░ 12% Wartość sprzedaży: 13 500 PLN Wpłaty: 13 500 PLN ✓ OK [... kolejne zamówienia ...] ──────────────────────────────────── Raport on demand: odpowiedz "szczegóły ZK#1201" lub "lista zaległości"
⚡Jak to działa
Propozycja▶
  • 1
    Scheduled job (codziennie rano) — agent odpytuje system magazynowy o wszystkie aktywne ZK danego PH.
  • 2
    Agregacja danych — dla każdego ZK: wartość umowna, suma WZ (koszt wydanych), wartość sprzedaży, suma wpłat. Oblicza różnicę i kolorystyczny status.
  • 3
    Generowanie wiadomości — Claude formatuje czytelne zestawienie. Priorytetyzuje: najpierw zaległości i alerty.
  • 4
    Wysyłka — mail lub SMS do PH. Opcjonalnie: raport dostępny pod linkiem.
  • 5
    Raport on demand — PH odpowiada na maila "szczegóły ZK#1201" → agent generuje pełny raport dla konkretnego zamówienia.
💡Ta automatyzacja wymaga tylko odczytu z systemu + maila. Nie dotykamy danych, nie zmieniamy statusów. Najszybsza do wdrożenia.

Tech▶

DaneAPI lub export systemu magazynowego — ZK + WZ + płatności per PH
FormatowanieClaude API — dane strukturalne wchodzą, czytelna wiadomość wychodzi. claude-haiku-4-5 (tanie, szybkie).
WysyłkaSMTP (mail) — najprostsze, żadnej zależności. SMS przez Twilio jeśli PH woli telefon.

5 Małe automatyzacje

Finalizacja:
ZK vs WZ i FV finalna

Koniec projektu: agent porównuje wartość umowną ZK z sumą wystawionych WZ, wylicza rzeczywistą marżę, identyfikuje pozycje gdzie jest różnica i generuje FV finalną na "ostatki".

⚡Jak to działa
Propozycja▶
  • 1
    Zestawienie ZK vs suma WZ — agent pobiera wszystkie WZ dla danego ZK i sumuje. Porównuje z wartością umowną.
  • 2
    Wyliczenie rzeczywistej wartości sprzedaży — różnica między umową a wystawionym. Agent wskazuje które pozycje się różnią.
  • 3
    Wyliczenie rzeczywistej marży — przychód realny minus koszt WZ = marża. Porównanie z planowaną marżą z ZK.
  • 4
    Podsumowanie do akceptacji — właściciel/PH widzi: "Różnica: +2 300 PLN (zmiana zakresu 12.07). Akceptujesz?" Wymagana decyzja człowieka.
  • 5
    Generowanie FV finalnej — po akceptacji: FV na pozostałą kwotę (model 90%+10%). Lub FV korekcyjna jeśli projekt był wyceniony za dużo/za mało.
❓Pytania otwarte
Do wyjaśnienia▶
Skąd agent wie że projekt skończony?Zmiana statusu ZK ręcznie, czy jest jakiś sygnał (ostatnie WZ, podpis odbioru)?
Kto zatwierdza różnice?Właściciel, PH, automatycznie jeśli różnica poniżej X%?
FV finalna — w jakim systemie?Czy można ją wygenerować przez API systemu fakturowania, czy to zawsze ręczna operacja?
6 Duże kontrakty · Kolejna faza

Duże procesy:
spłaszczanie i dzielenie wsteczne

Przy kontraktach z GW — te same mechanizmy transformacji danych co przy małych, ale większa skala i format narzucony przez zleceniodawcę. Odkładamy na fazę 2.

📦Co tu wchodzi
▶
  • Szablon zamówienia do klienta (GW) — na bazie systemu magazynowego, format narzucony przez GW
  • Tabelki od wykonawcy → podział na etapy, mapowanie pozycji
  • Spłaszczanie elementów — wiele pozycji WSW → jedna jednostka przeliczeniowa (czynność / m²)
  • Dzielenie wsteczne — jednostka z umowy GW → rozbicie na pozycje WSW z wartościami
  • Protokoły miesięczne narastające — format: do końca poprzedniego okresu / w okresie / narastająco (jak kontrakt NDI)
⏸️Ten blok jest dobrze zrozumiany z pierwszego spotkania. Realizacja po domknięciu automatyzacji #1–5.
🏗 Techniczne

Architektura rozwiązania

Sześć klocków, jeden fundament. System magazynowy jako jedyne źródło prawdy — agent nie duplikuje danych, tylko je odczytuje i przetwarza.

🗺️Jak klocki są połączone
▶
  • Fundament: system magazynowy — źródło ZK, WZ, cennika, płatności. Agent TYLKO odczytuje (nie pisze, dopóki nie będzie pewni że API jest stabilne).
  • Google Calendar API — jeden kierunek: agent wpisuje eventy, nie czyta (na start).
  • Mail (SMTP) — wychodzące powiadomienia i raporty. Brak odbierania (na start). Raport on demand przez prosty formularz web.
  • Claude API — Vision (scan projektu), formatowanie raportów, weryfikacja umów. Nie liczy — to robi Python.
  • Jedna aplikacja web — użytkownik otwiera i wybiera klocek. Nie 6 osobnych narzędzi.
  • Lokalna baza (SQLite) — historia ZK, poprzednie oferty, klucze marż, log powiadomień. Niezależna od systemu magazynowego.
🔀Kolejność budowania
▶
  • 1
    Auto #4 — dzienne summary PH — tylko odczyt z systemu + mail. Zero zapisu, zero ryzyka. Efekt widoczny od razu.
  • 2
    Auto #1 — oferta z ZK — potrzeba: plik Tomasza + cennik CSV + szablon oferty. Największy efekt dla klienta.
  • 3
    Auto #3 — monitoring WZ i powiadomienia PH — rozbudowanie #4 o trigger przy zmianie WZ.
  • 4
    Auto #5 — finalizacja — po tym jak mamy historię WZ w lokalnej bazie.
  • 5
    Auto #2 — umowa i Calendar — Google Calendar API, weryfikator umów.
  • 6
    Auto #6 — duże kontrakty — spłaszczanie, dzielenie wsteczne, protokoły.
